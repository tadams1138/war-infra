## 1. Overview

The Default UI is a **fully static** single-page application (SPA) that serves as the baseline frontend for all Wars that do not have a custom UI registered. It is built at compile time and deployed as static files to a CDN — there is no server-side rendering.

All data is fetched at runtime from the War REST API. The UI contains no business logic — it renders what the API returns.

---

## 2. Architecture Principles

- **Static files only.** Build output is plain HTML, CSS, and JavaScript. No Node.js server, no SSR, no edge functions.
- **CDN-hosted.** Assets are deployed to a CDN and served from the edge.
- **API consumer.** All data comes from `war-api` via `fetch()` calls. No data is computed or stored in the UI.
- **No business logic.** Scoring, matchup ordering, ranking — all returned by the API. The UI renders it.
- **Token storage.** JWT stored in memory (JavaScript variable). Refresh token stored in an `httpOnly` cookie set by the API. Never `localStorage`.
- **Client-side routing.** A single `index.html` is served for all routes; the SPA router handles navigation. The CDN/infra layer must rewrite all paths to `index.html` (see `war-infra` spec).

## 4. Routing & Pages

All routes are client-side. The CDN rewrites all paths to `index.html`.

| Route | Page | Auth required | Description |
|---|---|---|---|
| `/` | Home | No | Browse active public Wars |
| `/wars/:id` | WarDetail | No | War overview, contestant gallery |
| `/wars/:id/vote` | VoteMode | Yes | Binary matchup voting |
| `/wars/:id/rankings` | Rankings | No | Leaderboard |
| `/wars/new` | CreateWar | Yes | War creation wizard |
| `/my-wars` | MyWars | Yes | Voter's Wars |
| `/login` | Login | No | OAuth provider selection |

Unauthenticated users visiting a protected route are redirected to `/login` with a `returnTo` query param.

## 5. API Integration

All API calls are encapsulated in `src/api/client.ts`. Pages and components **never call `fetch()` directly** — they use typed functions from this module.

### 5.1 Types are generated, not written

Request and response types are **generated from the API's OpenAPI document** (`war-api-spec.md` §11.2) using `openapi-typescript`, committed to the repo, and regenerated by `npm run generate:api`.

Hand-writing them across three independently deployed repos with no shared package makes contract drift the highest-probability integration failure — and the kind that passes every test in both repos and only appears in staging. CI fails if regenerating produces a diff, so a merged API change that this repo has not absorbed is caught at PR time rather than after deploy.

The same generated document drives the MSW mocks the acceptance tests run against (§10), so those tests exercise the real response shapes rather than shapes someone believed were real.

Only the thin wrapper functions below are hand-written; their signatures use the generated types.

### 5.2 Shared Runtime for Custom UIs

Custom UIs need the same client logic this repo already has — auth, single-flight refresh, error mapping, vote submission, media handling. Rather than duplicating it per brand or publishing a package, **this repo emits it as a second build artefact that custom UIs load directly over HTTP**.

```
vite build            → dist/                      the SPA (content-hashed assets)
vite build --lib      → dist/runtime/v1.js         standalone runtime (stable path)
                      → dist/runtime/v1.d.ts       types for custom UI authors
```

Both outputs compile from the **same source** in `src/api/` and `src/auth/`. The SPA imports it as modules; the library build wraps it as an ESM bundle exposing a `WarRuntime` global. There is one implementation, never two.

A custom UI consumes it with a script tag — same origin, no build-time dependency, no registry:

```html
<script type="module" src="/runtime/v1.js"></script>
```

**Why not an npm package.** A package would need its own repo or a publish step, a version bump per brand, and a redeploy of every custom UI to pick up a fix. Serving it from a stable URL means a runtime fix ships with the next default-UI deploy and **every custom UI has it immediately**, with no brand having to act. Given that the highest-risk logic in here is the refresh flow — where a mistake gets voters logged out (§7) — centrally patchable is worth more than independently pinnable.

**Three things this requires:**

1. **A stable path, not a hashed one.** `/runtime/v1.js` is the one exception to the content-hashing rule in `war-infra-spec.md` §7. It is served with `Cache-Control: public, max-age=600, stale-while-revalidate=86400` — cached hard, refreshed within ten minutes of a deploy, never blocking on revalidation.
2. **A major version in the path.** Breaking changes ship as `/runtime/v2.js` while `v1.js` keeps serving. Custom UIs opt into a major version and get every patch within it automatically. Only a major bump requires a brand to act.
3. **A published API surface.** The `v1` global's shape is a contract, documented in this repo and typed by the emitted `.d.ts`. Anything not on it is internal and may change in any deploy.

**The tradeoff, stated plainly:** custom UIs cannot pin a patch version, so a bad runtime deploy breaks all of them at once. This is mitigated by the runtime shipping through this repo's own pipeline — staging, smoke tests, then a manual production gate — and by the acceptance tests in §11 exercising it. It is a deliberate trade of independent pinning for universal patchability.

```typescript
// Example typed API functions
getWars(params: GetWarsParams): Promise<WarListResponse>
getWar(warId: string): Promise<WarDetailResponse>
joinWar(warId: string): Promise<void>
getNextMatchup(warId: string): Promise<NextMatchupResponse | null>  // null = completed
castVote(warId: string, matchupId: string, winnerId: string): Promise<void>
getProgress(warId: string): Promise<ProgressResponse>
getRankings(warId: string): Promise<RankingsResponse>
createWar(payload: CreateWarPayload): Promise<WarResponse>
```

The client module automatically:
- Attaches `Authorization: Bearer <jwt>` from in-memory auth state
- Handles `401` responses by attempting a token refresh before retrying once
- Throws typed errors that map to user-facing messages (see §8)

## 6. Component Specifications

### MatchupView
The core voting UI. Displays two `ContestantCard` components side by side.

- Each card shows: primary image (full bleed), contestant name. **Vote cards show image and name only** — contestant attributes (§6, ContestantAttributes) appear on the War detail page, not here. Voting is a fast binary choice and extra text slows it down
- Images render as a `srcset` built from the `variants` array the API returns, with `sizes="50vw"` since two cards share the viewport. The browser then picks the 400px variant on a phone rather than downloading a 1600px one. URLs are never constructed client-side (`war-api-spec.md` §7)
- Reserve space using `aspect_ratio` from the media object so the cards do not shift as images load — layout shift under the tap target causes mis-votes
- On mount, prefetch the media named in the response's `prefetch` block so the next pair is already warm when the vote lands (`war-api-spec.md` §7.4)
- **The API decides which contestant is left and which is right** (`matchup.left` / `matchup.right`). The UI renders that order verbatim and must never shuffle, sort, or reorder the pair — doing so destroys the position-bias signal the API records (`war-api-spec.md` §9.3)
- Tapping/clicking a card casts a vote (calls `castVote`)
- While the vote is in-flight, both cards are disabled with a loading state
- After a successful vote, the next matchup is fetched automatically
- **Votes are final.** A voter is never served a pair they have already decided, so there is no in-flow path back to one. If a `409` is returned (only reachable via a stale tab or double-submit), the UI advances to the next matchup rather than surfacing an error — the vote it conflicts with is the voter's own
- There is no skip or abstain control. Leaving a pair undecided means navigating away; nothing is recorded (`war-api-spec.md` §9.2)
### ImageCarousel

Shown within a `ContestantCard` when a contestant has more than one image (up to 10, `war-api-spec.md` §7.3).

- The primary image (`display_order: 0`) is shown first; dot indicators appear only when there is more than one
- **Horizontal swipe within the card browses images. Tap votes.** These must not be confusable: a gesture is a swipe once it exceeds ~10px horizontally, and a swipe **never** casts a vote, however it ends. A mis-fired vote is unrecoverable — votes are final (`war-api-spec.md` §9.1) — so ambiguity resolves toward "swipe", never toward "vote"
- Arrow controls are rendered alongside the dots for pointer and keyboard users; the carousel is reachable by keyboard with arrow keys, and the card remains a single tab stop
- **Non-primary images load lazily**, on first navigation toward them. A 90-contestant War with 10 images each is 2,700 stored objects; eagerly loading every image for both cards would multiply per-matchup transfer roughly tenfold for images most voters never look at
- Swiping does not pause or reset anything — there is no timer on a matchup

### ContestantAttributes

Renders the resolved `attributes` array from the API (`war-api-spec.md` §5) as a simple label/value list, in the order the array supplies.

- Used on the **War detail page's contestant gallery only** — not on vote cards, and not in rankings
- Renders whatever fields the War declared, with no knowledge of what they mean. A pageant's Country/Age/Height and a primary's Party/State/Office use the identical component
- Values render as text. A `url`-typed value renders as a link with `rel="noopener noreferrer"`
- Fields the contestant omitted are skipped, not rendered blank

### MatchupView — video mode

When the War's `media_mode` is `video` (`war-api-spec.md` §5), the two cards hold embedded players instead of images and play **one after the other**.

**Playback sequence**

1. Both players are created paused, showing their poster images
2. The voter presses play once, on the pair — a single gesture, not one per video
3. The **left** video plays to its end
4. The **right** video then starts automatically
5. When it ends, both cards become selectable

Playback order follows display order, and the side assignment is already randomised per voter and recorded (`war-api-spec.md` §7.4). **The video that plays first is therefore randomised too, and which one it was is recoverable from `presented_left_id`** — order-of-play bias is measurable with machinery that already exists, and needs no separate mechanism.

**Voting is disabled until both videos have played once.** A replay control is always available for either video. Enabling the vote earlier would let voters decide before seeing the second contestant at all — and while randomised order means that bias cancels in aggregate, it adds avoidable noise to every pair.

**Autoplay is not guaranteed.** Browsers block programmatic playback with sound absent a user gesture, and mobile Safari is stricter than desktop about how far one gesture carries. The chain must therefore degrade rather than stall: if starting the second video is refused, show a play control on that card and wait for a tap. Never leave a voter looking at a paused player with no way forward.

**Unavailable videos do not block the vote.** A third-party video can be deleted or made private after it was validated (`war-api-spec.md` §11.3). When a player reports it unavailable, show an unavailable state on that card and **enable voting anyway** — otherwise one broken link would stall every matchup that contestant appears in, which is up to `n − 1` pairs.

**Privacy.** YouTube is embedded through `youtube-nocookie.com`. Players are created only for the current matchup and destroyed when it is replaced; `prefetch` carries poster images only, never a second player.

### ProgressBar
Displays `voted / total` matchups as a percentage bar and text label ("7 of 253").

`total` is every pair in the War. For large Wars that number is high by design — a 90-contestant War has 4,005 pairs — and finishing is not expected. Copy should frame progress as contribution rather than an unfinished task, and the UI must never imply a voter's partial contribution is wasted; unvoted pairs simply don't count.

### RankingsTable
Renders the leaderboard returned by `GET /rankings`. Columns: Rank, Image, Name, Wins, Appearances.

- Ranked by raw win count — no percentages are displayed or computed (`war-api-spec.md` §8)
- The UI performs **no ranking arithmetic**. It renders `rank`, `wins`, and `appearances` exactly as returned
- Polls the API every 30 seconds while the War is `active`; responses are cached 30s server-side, so polls are cheap
- Unranked contestants (`rank: null`, zero appearances) displayed at the bottom with "—" in the rank column

### WarCard
Summary tile used on the Home and MyWars pages. Displays: title, category badge, status badge, contestant count, time remaining (if `ends_at` is set).

### CreateWar Wizard
Multi-step form:
1. **Metadata** — title, category, visibility, optional end date
2. **Contestants** — add contestants one at a time (name, bio, upload images)
3. **Review** — summary of all contestants and images
4. **Activate** — calls `POST /activate`; on success, redirects to the War's vote page

## 7. Auth Flow

1. User visits `/login`
2. Clicks a provider button → browser navigates to `GET /api/v1/auth/{provider}/login`
3. Provider redirects back to the API callback → API sets the `httpOnly` refresh cookie and redirects to `/auth/callback`, **carrying no token**
4. The `/auth/callback` route calls `POST /auth/refresh` (cookie sent automatically), receives the JWT in the response body, stores it in memory, and redirects to `returnTo`
5. On JWT expiry, the client module silently calls `POST /auth/refresh` and retries the original request once
6. Logout calls `DELETE /auth/session` and clears the in-memory JWT

**No token ever appears in a URL** — not in the path, query, or fragment (`war-api-spec.md` §4.1). The SPA must never read a credential from `location`.

**Refresh is single-flight.** Concurrent 401s must trigger exactly one `POST /auth/refresh`; other in-flight requests await that result and then retry. Firing several refreshes in parallel would rotate the token repeatedly, and the losing requests would present an already-used token — which the API treats as theft and responds to by revoking the whole family (`war-api-spec.md` §4.2), logging the voter out.

**A failed refresh is terminal.** Clear the in-memory JWT and redirect to `/login` with `returnTo`. Never retry a refresh.

## 8. Error Handling

Error handling is uniform across all pages. The `api/client.ts` module throws typed errors; pages render appropriate UI states.

| API Status | User-facing message |
|---|---|
| `401` | "Please log in to continue" → redirect to `/login` |
| `403` War closed | "This War is locked — voting is closed" |
| `403` Not joined | "Join this War to vote" |
| `404` | "This War doesn't exist or has been removed" |
| `409` Already voted | No message — silently advance to the next matchup (see MatchupView, §6) |
| `429` Rate limited | "Slow down a moment — try again in {Retry-After}" and re-enable after that delay. Never presented as an error |
| `422` | "Something went wrong — please try again" |
| `5xx` | "Server error — please try again shortly" |
| Network failure | "Unable to reach the server — check your connection" |

## 12. Implementation Status

This document specifies the full default UI across all seven routes, both media modes, and
the shared runtime artifact for custom UIs. As of 2026-08-31, the Core Voting Loop slice
below is **implemented and live in both staging and production** (`war-ui-default`'s
placeholder "coming soon" page is gone), verified with a real interactive Google login, not
just automated tests. This section marks the boundary that slice draws: what it covers,
versus what remains spec-only until a later slice picks it up.

**Shipped in this slice — the Core Voting Loop:**

- Home (`/`): browse active public Wars. War cards show title, category, and contestant
  count — not the status badge or time-remaining fields WarCard (§6) also describes; those
  wait for the slice that actually needs them.
- Login (`/login`) and the auth flow (§7): OAuth provider selection, JWT held in memory
  only, refresh-cookie exchange at `/auth/callback`, single-flight refresh on `401`, and a
  terminal failed-refresh path that clears the JWT and redirects to `/login`. Provider
  buttons render for the full list in `war-api-spec.md` §4, but only Google is live on the
  API side (`war-api-spec.md` §15) — the other four 404 until the API adds them. The OAuth
  callback's failure responses (declined consent, provider errors) currently land the user
  on raw API JSON mid-redirect — functionally correct, UX-rough; see
  `war-infra-spec.md` §20.5 for the deferred redirect-based failure UX this UI would need
  a page for.
- WarDetail (`/wars/:id`): War overview and contestant gallery, image mode only, plus
  ContestantAttributes (§6) rendering the resolved schema.
- VoteMode (`/wars/:id/vote`) (§6): MatchupView, ContestantCard, ImageCarousel, and
  ProgressBar — **image mode only**; video mode is spec-only in this slice ("MatchupView
  — video mode"). Navigating here silently joins the War on first entry (`joinWar`, §5.2)
  rather than exposing a separate Join control — the "403 Not joined" row in §8 is a
  defensive fallback for that join call racing or failing, not the normal path.
- `api/client.ts` (§5): typed wrapper covering exactly the endpoints this slice calls — wars
  list, war detail, next-matchup, cast-vote, join, and the auth endpoints. Types are
  generated from war-api's live `GET /api/v1/openapi.json` (§5.1) — that document, and the
  `contestant_count`/vote-403-`reason` fields this slice needed from it, were themselves
  built as small preceding `war-api` changes once the gap was found mid-implementation
  (`war-api-spec.md` §11.2/§11.2.1, §15).

**Deferred — spec-only, no scope in this slice:**

- Rankings (`/wars/:id/rankings`) and RankingsTable (§4, §6)
- CreateWar wizard (`/wars/new`) (§4, §6)
- MyWars (`/my-wars`) (§4)
- Video-mode matchups — MatchupView's video playback sequence (§6)
- The shared runtime build artifact for custom UIs, `dist/runtime/v1.js` and `dist/runtime/v1.d.ts` (§5.2)

None of the above is inferred to be in scope from a component or route already being named
in this document — a section describing the full design does not mean every part of it has
been built.

**§11's Gherkin covers the full design**, including scenarios for pages and modes not yet
built (Rankings, Create War, and the video-mode scenarios under "Video Matchups"). The
scenarios that actually apply to this slice live in `war-ui-default/features/*.feature` — a
repo-local, in-scope-only adaptation of a subset of §11, which the implementer binds into
Playwright specs under `tests/acceptance/`. That directory is executable test fixture, not a
second copy of this document; it does not duplicate the prose here and should not be read as
such.

This section is the status marker for what this slice covers. Update it — not by forking a
second prose document in `war-ui-default` — as further slices land.
